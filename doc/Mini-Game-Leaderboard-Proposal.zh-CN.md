# NKAS 小游戏与排行榜方案

## 目标

在 NKAS Web UI 中增加一个轻量小游戏，并提供成绩记录与排行榜。首版优先服务于同一台 NKAS 服务及其局域网访问者，暂不引入独立账号系统和公网对战服务。

## 玩法候选

| 游戏 | 核心玩法 | 开发量 | 排行榜适配 |
| --- | --- | --- | --- |
| 合成小妮姬 | 相同等级的角色或装备合成更高等级，类似合成大西瓜 | 中 | 有趣，但客户端物理和成绩校验较复杂 |
| NIKKE 靶场 | 限时点击目标，按命中率、连击和反应速度计分 | 低 | 最适合首个排行榜版本 |
| 弹药装填挑战 | 在节奏点完成装填，连续成功获得倍率 | 低 | 规则简单，适合每日挑战 |
| 角色记忆牌 | 翻牌配对，按用时和错误次数排名 | 低 | 轻量，但成绩区分度有限 |
| 小型躲避战 | 操作角色躲避攻击，坚持时间越长分数越高 | 中高 | 可玩性高，需要更多动画和碰撞逻辑 |

## 推荐方案：合成小妮姬

合成玩法与“合成大西瓜”接近，但使用 NIKKE 主题进行包装。为提高排行榜公平性，建议采用每日固定挑战，而不是完全自由的无限模式：

- 每局限定 90 或 120 秒。
- 每天使用固定随机种子，所有玩家的掉落序列一致。
- 相同等级的角色或装备合成后升级并获得分数。
- 连续合成提供 Combo 倍率，鼓励主动规划而不是单纯等待。
- 记录每日榜、周榜和总榜。
- 结算时保存随机种子、掉落序列、最终分数和游戏版本。

等级素材可以先使用简单图标占位，之后再替换为 NIKKE 角色、装备或物资图。这样玩法和数据结构不会依赖具体素材，便于后续美术迭代。

## 更容易验证的备选：NIKKE 靶场

如果优先目标是尽快验证排行榜基础设施，靶场挑战更适合作为第一款游戏：

- 固定 30 秒挑战时间。
- 目标按固定种子生成，目标大小和出现位置可由服务端下发。
- 分数由命中、连击、剩余时间和误击共同决定。
- 客户端提交命中事件序列，服务端可重新计算成绩。

相比合成玩法，靶场的状态空间更小，提交记录也更容易复核，适合先验证接口、存储、赛季和排行榜 UI。

## 数据存储

统计数据继续放在现有 `data/` 目录体系下。排行榜不建议使用 CSV：排行榜需要频繁追加、排序、去重、分页，并且可能同时收到多个浏览器或进程的提交。建议使用 Python 内置 SQLite：

```text
data/
  mini_game/
    leaderboard.sqlite3
    player.json
    replays/
  nkas/
    items.csv
    stones.csv
```

排行榜数据库可以包含以下两张表：

### `game_runs`

保存每一局原始成绩，便于查看历史和复核异常成绩。

```text
id
game_id
player_name
score
duration_ms
seed
season
client_version
created_at
replay_data
```

### `leaderboard_entries`

保存每个玩家在每个游戏、赛季中的最佳成绩，避免每次查询都扫描全部历史记录。

```text
game_id
season
player_name
best_score
best_run_id
updated_at
```

排行榜范围需要明确：本地安装只能形成“本机排行榜”；局域网用户访问同一个 NKAS 后端时可以共享排行榜；公网榜则需要额外的账号、鉴权、限流和更严格的反作弊服务。

## 后端接口草案

沿用当前 Starlette REST API 风格：

```text
GET  /api/minigame/games
GET  /api/minigame/{game_id}/leaderboard?season=daily&limit=50
POST /api/minigame/{game_id}/runs
GET  /api/minigame/{game_id}/history?player=...
```

提交成绩的请求体可包含：

```json
{
  "player_name": "Commander",
  "score": 12345,
  "duration_ms": 90000,
  "seed": "2026-09-03",
  "events": [],
  "client_version": "0.1.0"
}
```

服务端至少应校验游戏 ID、分数范围、时长范围、玩家名长度和请求频率。首版可以接受“本地可信”模型，不必把反作弊做到公网竞技级别；但保留 `seed`、`events` 和 `client_version` 字段，方便以后升级校验逻辑。

## Web UI 入口

增加 `/minigame` 路由和一个侧边栏入口，使用现有 `gamepad` 图标。页面建议分成三个区域：

1. 游戏区：Canvas 或固定尺寸的游戏容器。
2. 成绩区：当前分数、个人最佳、剩余时间和结算按钮。
3. 排行榜区：日榜、周榜、总榜切换，以及自己的排名。

页面文本继续接入现有 i18n，游戏素材放在 `assets/mini_game/`，避免把业务逻辑和设备自动化模块混在一起。

## 分阶段实施

1. 实现排行榜存储层和 REST 接口，先用靶场或模拟数据验证提交、查询、分页和赛季切换。
2. 增加 `/minigame` 页面、玩家昵称设置和历史成绩展示。
3. 实现合成小妮姬的固定种子模式。
4. 增加排行榜异常分数标记、成绩撤销和数据导出。
5. 若确实需要公网共享，再单独设计账号和远程排行榜服务，不把公网依赖写死在 NKAS 核心程序中。

## 结论

长期主玩法建议采用“合成小妮姬”，它最符合休闲小游戏的期待，也有足够的扩展空间。工程上建议先以“NIKKE 靶场”验证排行榜链路，再复用同一套存储和接口接入合成玩法。
